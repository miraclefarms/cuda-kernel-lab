# S0 基座

## 01｜三台机器不是三块显卡，是三种约束

**主张**：优化决策的起点不是架构代号，而是 ridge point 与 SM 资源预算。同为 `sm_90a`
的 H20 和 H200，该做的优化不是同一件事。

**章节**
1. 「Hopper 优化」这个说法为什么没有意义 —— 用三机 ridge point 表开场
2. SM 的四种预算：寄存器、SMEM、warp slot、block slot —— 资源模型
3. occupancy 神话：100% 从来不是目标，它真正限制的是什么
4. grid 该按问题规模定，还是按 SM 数定 —— 两种范式与各自适用面
5. 三机基线画像：`bench-probe` 读到的与 datasheet 的出入
6. occupancy 曲面：寄存器数 × SMEM 用量如何决定驻留块数（静态扫描）
7. 这张基线表是后面 18 篇的分母

**实验**：`bench-probe` 三机 + `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 扫描。
纯 API 查询，不涉及计时，因此不依赖尚未交代的测量方法论。

**零件**：`environment-matrix.md` 填实 + occupancy 扫描脚本

**承接**：开篇。下启 02 —— 既然要跨机比较，先得有可信的测量。

## 02｜一个可信的数字需要多少纪律

**主张**：大量 CUDA 性能结论不可复现，原因集中在四件事：没 flush L2、没锁频、报了均值、
混了冷热口径。

**章节**
1. 一次失败的测量：不 flush L2 的 triad 能「跑出」多少虚假带宽
2. cold 与 hot：两个都对，但回答的是不同问题
3. CUDA Graph 计时：把启动开销从被测对象里摘出去
4. 锁不了频怎么办 —— 相对比值、分位数、时钟记录
5. ncu 计数器：拿得到与拿不到时，各自能说什么、不能说什么
6. harness 的实现与 CSV 契约
7. 把 triad 重测一遍：有纪律与没纪律差多少

**实验**：同一个 triad，无纪律版 vs 有纪律版，三机。第 1 节的「虚假带宽」本身就是数据。

**零件**：`bench/` harness 定稿 + CSV schema + 四项接口约定初稿

**承接**：上承 01 的比较需求；下启 03。

## 03｜搬运范式的分水岭：`cp.async` 与它的天花板

**主张**：内存层级的瓶颈不在容量，而在「谁来搬、搬的时候谁在等」。

**章节**
1. global → L2 → SMEM → 寄存器：每层的容量与代价
2. 合并访问与 sector：128B 事务的真实含义
3. 同步搬运的代价：`ld.global` + `st.shared` 为什么卡住整个 warp
4. `cp.async`（`sm_80`）：第一次把搬运变成异步
5. 三机实测：不同 tile 形状下 `cp.async` 的收益与失效点
6. `cp.async` 的三个局限：地址计算仍在 SM、多维 tile 仍要手算、边界仍要手判
7. 这三个局限正是 TMA 要解决的

**实验**：SMEM staging microbenchmark，三机，扫 tile 形状与访问模式。

**零件**：SMEM staging 模板

**承接**：上承 02 的 harness；下启 04（第 6 节直接列出 TMA 的动机清单）。A100 在这篇是
主角之一，不是陪跑。

# S1 异步与流水线

## 04｜TMA：把地址计算交给硬件

**主张**：TMA 的价值不是「更快的 memcpy」，而是把多维索引与边界处理整体挪出 SM。

**章节**
1. 描述符：把 tensor 的形状一次性告诉硬件
2. 多维 tile 与隐式边界处理 —— 省掉的不只是指令，还有寄存器
3. swizzle：SMEM 布局为什么必须与后续 MMA 的期望对齐
4. 一次 TMA 搬运的完整生命周期：发起、到达、消费
5. 与 `cp.async` 的对照实测：什么规模上 TMA 才开始赢
6. TMA 的固定开销与失效边界 —— 小 tile 上为什么反而亏
7. 只会搬还不够：搬运必须连成流水

**实验**：TMA vs `cp.async`，H20/H200；A100 跑 `cp.async` 版作为「TMA 之前」对照。扫
tile size 找交叉点。

**零件**：TMA 描述符构造封装 —— **接口约定 #1 在此落地**

**承接**：上承 03 的局限清单；下启 05。

## 05｜mbarrier 与流水线深度

**主张**：异步搬运只有连成流水才产生收益，而流水深度是一个有最优点、且最优点随机器
变化的可调参数。

**章节**
1. `mbarrier` 的语义：phase、arrive、`expect_tx`
2. 从双缓冲到多级缓冲：SMEM 预算怎么被吃掉
3. 深度与 occupancy 的对抗：更深的流水买来更少的驻留块
4. 正确性先行：常见的 barrier 竞态与它们的症状
5. 深度扫描实测：H20 与 H200 的最优深度不同
6. 延迟已经藏住之后，继续加深为什么没有收益
7. 生产者与消费者仍挤在同一批线程里

**实验**：pipeline 深度 2/3/4/6 扫描 × tile 形状，H20/H200。

**零件**：多级 pipeline 模板 —— **接口约定 #2 在此落地**

**承接**：上承 04 的单次搬运；下启 06。

## 06｜Warp specialization：让线程分工

**主张**：把搬运与计算交给不同的 warp，比让同一批线程轮流做两件事更能填满流水；但这
条结论在算力受限的机器上会翻转。

**章节**
1. 统一分工为什么浪费寄存器
2. producer / consumer 的角色划分与 barrier 协议
3. `setmaxnreg`：在角色之间重新分配寄存器预算
4. warp group 与调度：到底谁在等
5. 实测：WS 版本 vs 第 05 篇的统一版本
6. **H20 与 H200 的收益反号点** —— 全系列核心论点的第一次正面验证
7. 分工之后，数据还能不能跨 CTA 共享

**实验**：WS vs non-WS，H20/H200，扫 tile 形状与流水深度，定位反号点。

**零件**：WS kernel 骨架

**承接**：上承 05；下启 07。

## 07｜Cluster、DSMEM 与 TMA multicast

**主张**：cluster 把「SM 之间」变成可编程层级，收益高度依赖数据复用度，不复用就是纯
同步开销。

**章节**
1. thread block cluster：调度保证与它的代价
2. DSMEM：一个 CTA 直接读另一个 CTA 的 SMEM
3. TMA multicast：一次搬运喂多个 CTA
4. cluster 尺寸怎么选：2 / 4 / 8 与 SM 数的关系
5. 实测：开关 multicast 的有效带宽放大比
6. 失效边界：复用度不足时同步代价吃掉全部收益
7. A100 上的等价写法与它的代价

**实验**：cluster GEMM 片段，H20/H200；A100 写 non-cluster 等价版作对照。

**零件**：cluster + multicast 模板

**承接**：上承 06 的跨 CTA 问题；下启 08。

## 08｜kernel 之间：PDL、CUDA Graphs 与 green context

**主张**：单 kernel 优化到头之后，下一块可回收的时间藏在 kernel 与 kernel 的缝隙里。

**章节**
1. 启动开销的真实量级 —— 用 02 篇的 harness 直接量
2. CUDA Graph：把一串 launch 变成一次提交
3. conditional node：把控制流放进图里
4. PDL：让下一个 kernel 提前开始
5. green context：把 SM 切给不同的工作
6. 实测：小 kernel 密集序列的端到端收益
7. 什么时候这些机制反而让事情更糟

**实验**：小 kernel 链（模拟 decode 循环），三机；PDL 部分仅 H20/H200。

**零件**：启动/重叠模板

**承接**：S1 收口。下启 S2 —— 延迟藏完了，接下来是算力有没有喂饱。

# S2 张量核心

## 09｜MMA 三代：从 `mma.sync` 到 `wgmma`

**主张**：每一代 MMA 都在解决上一代「喂不饱」的问题，而喂不饱的形式一直在变。

写法是**同一个 GEMM 两种实现正面对打**，历史只作论证骨架，保证这篇有自己的实验。

**章节**
1. `mma.sync`：warp 级同步矩阵乘，以及它的寄存器压力
2. 同一个 GEMM 的 `mma.sync` 实现与瓶颈定位（A100 / H200 实测）
3. `wgmma`：异步、warp group 级、操作数从 SMEM 直读
4. 同一个 GEMM 的 `wgmma` 实现（H20 / H200 实测）
5. 两代对打：H200 上的加速比来自哪几个具体变化
6. 为什么 A100 上的调优经验搬到 Hopper 会失效
7. accumulator 还留在寄存器里 —— 下一个瓶颈的伏笔

**实验**：同一 GEMM 两种实现，三机（A100 只能跑 `mma.sync` 版）。

**零件**：`mma.sync` 与 `wgmma` 两版 GEMM 基线

**承接**：上承 S1 的流水线；下启 10。

## 10｜`wgmma` 实战：寄存器预算的重新分配

**主张**：`wgmma` 的性能取决于能否把 accumulator 留在寄存器里，同时还留下足够的流水空间。
这是一个三方零和博弈。

**章节**
1. `wgmma` 的操作数来源与布局要求
2. accumulator 的寄存器占用如何随 tile 形状爆炸
3. tile 形状选择：算力、SMEM、寄存器的三方博弈
4. 与 S1 流水线的耦合：搬运深度 × MMA 形状的联合扫描
5. 实测：H20 与 H200 的最优 tile 形状不同，且不是简单缩放
6. 达成率：距标称峰值还有多远，差距分解到哪几项
7. 寄存器压力正是下一代硬件要解决的问题（伏笔）

**实验**：tile 形状 × pipeline 深度联合扫描，H20/H200。

**零件**：wgmma GEMM —— **接口约定 #3（accumulator 布局）在此落地**

**承接**：上承 09；下启 11。

## 11｜FP8 的数值学

**主张**：FP8 的两倍算力不是白给的，代价是你必须自己管理动态范围。

**章节**
1. E4M3 与 E5M2：两种取舍分别适合什么位置
2. scaling 粒度：per-tensor / per-block / per-channel
3. 误差从哪来：量化误差、累积误差、异常值放大
4. scale 的存储与广播代价 —— 常被忽略的那部分开销
5. 实测：FP8 vs BF16 的加速比与精度损失曲线
6. **H20 与 H200 上 FP8 的价值不同**：算力受限机器上 FP8 才是主菜
7. 什么时候 FP8 不划算

**实验**：FP8 GEMM vs BF16 GEMM，H20/H200，扫 scaling 粒度 + 误差统计。

**零件**：量化/反量化 + scale 布局

**承接**：上承 10；下启 12（反量化放哪儿 → epilogue）。

## 12｜Epilogue 融合的边界

**主张**：融合省下的是访存，花掉的是寄存器。这个交换有一个明确的翻转点，且翻转点随
机器的 ridge point 移动。

**章节**
1. 不融合的代价：一次写出 + 一次读回
2. 可融合操作的谱系：反量化、激活、bias、reduction
3. 寄存器代价：融合链变长时 occupancy 怎么掉
4. reduction 类 epilogue 的特殊性：跨 CTA 同步
5. 实测：融合链长度 × 性能曲线与拐点
6. 三机对照：带宽受限的机器上融合更值
7. 可组合 epilogue 的接口设计

**实验**：融合链 0/1/2/3 级扫描，三机。

**零件**：可组合 epilogue —— **接口约定 #4 在此落地，四项约定至此全部实战验证**

**承接**：S2 实测部分收口；下启 13。

**章节**

7. 它是 CUTLASS 的地基

## 16｜cuTile：tile 抽象抽掉了什么，又漏出了什么

**主张**：Tile 编程模型把 tensor core 抽象掉了，但没有、也不可能抽掉 ridge point。
